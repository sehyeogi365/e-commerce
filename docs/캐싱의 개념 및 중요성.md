1.	캐싱의 개념 및 중요성<br><br>
      o	캐시란 데이터를 임시로 저장하여 빠르게 응답하고 DB 부하를 줄이는 기술.<br><br>
      o	DNS, CPU 캐시, CDN 등 다양한 사례를 설명.<br><br>
      o	서버 내 메모리 캐시와 외부 캐시 서비스(예: Redis, CDN) 비교.<br><br>
2.	서버 캐싱 전략<br>
      o	메모리 캐시 (Application Level)<br><br>
      &nbsp; 	Spring 및 Nest.js에서의 캐싱 코드 예시 제공.<br><br>
      &nbsp; 	장점: 속도 빠름, 네트워크 비용 없음.<br><br>
      &nbsp; 	단점: 분산 환경에서 데이터 불일치 가능성, 애플리케이션 종료 시 캐시 삭제.<br><br>
      o	외부 캐시 서비스 (External Level)<br><br>
      &nbsp;	Redis 같은 외부 스토리지 사용으로 일관성과 안정성 강화.<br><br>
      &nbsp;	장점: 분산 환경에서도 안정적, 장애 복구 가능.<br><br>
      &nbsp;	단점: 네트워크 통신으로 비용 증가.<br><br>
3.	캐싱 전략 및 종료 타입 <br><br>
      o	Cache-Aside(Lazy Loading)<br><br>
      &nbsp;	앱에서 데이터를 읽는 전략이 많을 때 사용하는 전략이다. 이 구조는 Redis를 캐시로 쓸 때 가장 일반적으로 사용하는 방법이다. 캐시는 찾는 데이터가 없을 때 DB에 직접 조회해서 입력되기 때문에 Lazy Loading이라고 한다.<br><br>
      &nbsp;	사용사례 : 캐시 관리가 애플리케이션의 통제하에 있을 때 사용됩니다.<br><br>
      &nbsp; 	적용 : 주문조회, 결제내역<br><br>
      &nbsp; 	적용 이유 : 주문 정보, 결제 내역은 일관성이 중요한 데이터이므로 캐시에 보관하기보다는 필요할 때 캐싱하는 Cache-Aside가 적절.<br><br>
o	Read-Through<br><br>
&nbsp;	Read-Through 전략은 데이터를 읽을 때 캐시로만 데이터를 읽어온다. 만약 Cache Miss가 발생하면 DB에서 해당 데이터를 캐시에 바로 저장한다. 즉 캐시는 앱과 DB 중간에 위치해 앱은 캐시만 바라보게 되고 DB는 캐시만 바라보게 된다.<br><br>
&nbsp;	사용사례 : 자주 읽히는 데이터를 빠르게 제공하기 위해 사용됩니다.<br><br>
&nbsp;	적용 : 상품조회, Top5 상품조회<br><br>
&nbsp; 	적용 이유 : 자주 조회되는 데이터(상품 정보, 인기 순위)는 캐시 적중률을 높이는 게 중요하므로<br><br>
o	Write-Through<br><br>
 	Write-Through 전략은 DB에 데이터를 저장할 때 먼저 캐시에 기록된 다음 DB에 저장되는 방식이다.<br><br>
 	사용사례 : 데이터 일관성이 중요한 경우에 사용됩니다.<br><br>
 	적용 : 쿠폰 발급, 포인트 차감<br><br>
 	적용 이유 : 쿠폰은 한 번 발급되면 변경되지 않고, 빠르게 조회해야 하므로 DB와 캐시에 동시 반영하는 방식이 적합합니다.
o	Write-Behind<br>
&nbsp; 	쓰기 작업을 캐시에 먼저 저장했다가 특정 시점마다 DB에 저장하는 방식이다.<br><br>
&nbsp; 	사용사례 : 쓰기 작업이 빈번하지만 즉각적인 일관성이 필요하지 않은 경우에 사용됩니다.<br><br>
&nbsp; 	적용 : 포인트 충전/조회<br><br>
&nbsp; 	적용 이유 : 포인트 조회 작업은 빈번하지만, 일관성이 중요하지 않기 때문에 적합합니다.<br><br>
4.	캐시 스탬피드 현상<br><br>
o	캐시 스탬피트란?<br><br>
&nbsp; 	캐시가 만료되었을 때, 동시에 여러 개의 요청이 한꺼번에 DB나 원본 서버로 몰리는 현상.<br><br>
&nbsp; 	여러 클라이언트가 캐시 히트를 하지 못해 캐시 항목을 재계산하려고 할 때 발생하는 현상이다.<br><br>
o	발생 원인<br><br>
&nbsp;	애플리케이션이 look-aside 방식을 사용하여 키를 관리<br>
&nbsp;	한참 트래픽 높은 시간에 캐시가 만료<br>
&nbsp;	캐시 만료 시 동시 요청<br><br>
o	해결 방안  <br><br>
&nbsp;	적절한 만료 시간 설정<br>
      &nbsp;&nbsp;  -	만료 시간을 너무 짧게 설정 하지 않는다.<br>
  -	데이터 특성에 맞춰 설정<br><br>
&nbsp;	선 계산<br><br>
       &nbsp;&nbsp; -	키가 만료되기전에 갱신한다.<br><br>
&nbsp;	확률적 접근 <br><br>
       &nbsp;&nbsp;-	만료 시간이 가까워질수록 확률적으로 DB에 접근해 데이터를 갱신한다.<br><br>
       &nbsp;&nbsp;-	캐시 만료 시간을 분산해 여러 클라이언트가 동시에 캐시를 갱신하지 않는다.<br><br>
&nbsp;	PER 알고리즘 사용<br><br>
       &nbsp;&nbsp;-	캐시 만료되기 전에 일정확률로 캐시를 갱신한다.<br><br>
       &nbsp;&nbsp;-	캐시가 만료되기 전에 미리 갱신하여, 캐시 만료 시점에 부하가 집중되는 것을 방지하는 장점이있다.
