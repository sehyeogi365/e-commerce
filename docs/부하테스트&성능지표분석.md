1. 부하 테스트 대상 API 선정

선정 기준
-	동시성 이슈 발생 가능성
-	트래픽 집중 가능성
-	DB 부하 가능성
-	성능 병목 발생 가능성
-	SPOF(Single Point of Failure) 가능성

포인트 충전
POST /api/v1/point/charge
-	선정 이유:<br>
     	실시간 처리를 검증해야 해서<br>
     	데이터베이스 부하<br><br>

-	테스트 포인트:<br>
     	사용자 수에 따른 응답 시간

선착순 쿠폰 발급
POST /api/v1/coupons/receive
-	선정 이유:
     	쿠폰 발급시 과부하가 일어날 가능성<br>
     	실시간 쿠폰 수량 변경으로 동시성 이슈 일어날 가능성<br>

-	테스트 포인트:<br>
     	시스템 자원 사용량<br>
     	최대 동시 발급 인원수

상품 조회
GET /api/v1/products/select
-	선정 이유:<br>
     	실시간 상품 수량 조회등으로 인한 DB 부하<br>
     	다수의 사용자 조회 가능성<br>
     	동시성 이슈 가능성

-	테스트 포인트:<br>
     	DB부하<br>
     	사용자 수에 따른 응답 시간


결제처리
POST /api/v1/payment/
-	선정 이유:<br>
     	동시성 이슈가 일어날 가능성

-	테스트 포인트:<br>
     	동시성 몇 명때 부하 일어나는지
     	시스템 자원 사용량

import http from 'k6/http';
import { sleep } from 'k6';

    export default function () {
      http.get('https://test.k6.io');
      sleep(1);
    }

    export const options = {
      scenarios: {
          point_charge: {
                executor: 'ramping-vus',
                startVUs: 10,
                stages: [
                  { duration: '10s', target: 50 }, // 10초 동안 50명까지 증가
                  { duration: '20s', target: 100 }, // 20초 동안 100명까지 유지
                  { duration: '10s', target: 0 }, // 10초 동안 감소
                ],
                gracefulStop: '5s',
              },
              coupon_receive: {
                executor: 'constant-vus',
                vus: 200, // 200명 동시 요청
                duration: '20s',
              },
              product_select: {
                executor: 'ramping-arrival-rate',
                preAllocatedVUs: 50,
                stages: [
                  { duration: '10s', target: 100 }, // 초당 100건 요청 증가
                  { duration: '30s', target: 200 }, // 초당 200건 유지
                ],
              },
              payment_process: {
                executor: 'constant-arrival-rate',
                rate: 10, // 초당 10건 요청
                timeUnit: '1s',
                duration: '30s',
                preAllocatedVUs: 20,
              },
      },
    };

    const BASE_URL = 'http://host.docker.internal:8080/api/v1';
    export function customScenario() {
      let res;
      let scenario = __VU % 4; // 사용자별 테스트 분배

      if (scenario === 0) {
        res = http.post(`${BASE_URL}/point/charge/point/charge`, JSON.stringify({ userId: '123', amount: 1000 }), { headers: { 'Content-Type': 'application/json' } });
      } else if (scenario === 1) {
        res = http.post(`${BASE_URL}/coupons/receive`, JSON.stringify({ userId: '123', couponCode: 'NEWYEAR' }), { headers: { 'Content-Type': 'application/json' } });
      } else if (scenario === 2) {
        res = http.get(`${BASE_URL}/products/select`);
      } else {
        res = http.post(`${BASE_URL}/payment/`, JSON.stringify({ userId: '123', productId: 'A100', price: 5000 }), { headers: { 'Content-Type': 'application/json' } });
      }

      check(res, { 'status is 200': (r) => r.status === 200 });

      sleep(1);
    };

6. 성능 저하원인 분석 개선방안<br>
   6-1 원인 분석
-	데이터 베이스 부하
-	레디스 부하
-	Cpu나 다른 스펙문제
-	네트워크 지연<br><br>
     6-2 개선 방안
-	서버 스케일링: VUs 증가 시 정상 응답 유지 가능한지 확인
-	쿼리 최적화: 느린 API 확인 후 쿼리 튜닝 (인덱싱, 캐싱 활용)
-	로드 밸런싱: 트래픽 분산할 수 있도록 구조 개선
-	애플리케이션 로직 분석: 특정 API의 지연 원인 찾기 (예: product_select 요청이 빠른 반면, coupon_receive가 병목 가능성)
-   서킷 브레이커 적용: 외부 API 요청 시 서킷 브레이커(@CircuitBreaker) 패턴 사용

7-2 모니터링 결과분석
-	우선 비교적VU(virtual user)가 시간이 지날수록 떨어지는 모습, 절반이상이 떨어졌다.
-	Failed requests per Second는 0으로 변함이 없었다.
-	Aggregate http_req_duration, http_req_duration(요청에 걸린 총 시간) 또한 시간이 지날수록 감소하는 모습을 보였다.
