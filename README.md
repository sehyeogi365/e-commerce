# e-commerce

Day 1: 동시성 문제 이해하기 <br>
•	Race Condition: 여러 프로세스나 스레드가 동시에 공유 자원에 접근할 때, 실행 순서에 따라 결과가 달라지는 상태. <br>
예시: <br>
상품 수량 조회 및 결제시: 여러 사용자가 동일 상품을 결제시 재고 수량 정보가 올바르게 적용이안될 수 있음 <br>
쿠폰 발급 페이지 조회할 때: 다수의 사용자가 동시에 발급 요청을 처리할 경우, 한정된 수량 이상의 쿠폰이 발급될 수 있음.  <br>

해결법:  <br>
Locking: 자원에 접근할 때 뮤텍스(Mutex) 또는 세마포어(Semaphore)를 사용하여 동기화. <br>
Atomic Operation: 원자적 연산을 사용하여 상태를 일관성 있게 유지 <br>

•	Deadlock: 두 개 이상의 프로세스 또는 스레드가 서로 자원을 점유하고, 상대방의 자원을 기다리며 무한히 대기하는 상태. <br>
예시:  <br>
동일 상품을 여러 사용자가 주문/결제할 때. 또는 동일 쿠폰을 여러 사용자가 발급할 때 <br>
동일 쿠폰을 여러 사용자가 발급 요청할 때, 각 스레드가 자원을 점유하고 대기하는 상황. <br>

해결법:  <br>
Deadlock Prevention: 자원 할당 순서를 정하거나 타임아웃을 설정. <br>
Deadlock Detection and Recovery: 교착 상태를 탐지하여 프로세스를 강제로 종료하거나 자원을 해제. <br>

•	Dirty Read: 하나의 트랜잭션이 아직 커밋되지 않은 데이터를 다른 트랜잭션이 읽는 경우. <br>
예시:  <br>
쿠폰 발급이완료 안됐는데 쿠폰 수량 조회 시 잘못된 수량을 조회하게 됨 <br>
상품 결제가 완료 안됐는데 상품 수량 조회 시 잘못된 수량을 조회하게 됨 <br>
해결법: <br>
트랜잭션 격리 수준 설정: Read Committed 이상으로 설정하여 커밋되지 않은 데이터를 읽지 않도록 보장. <br>

•	Non-repeatable Read: 한 트랜잭션 내에서 같은 데이터를 두 번 읽을 때, 중간에 다른 트랜잭션이 데이터를 변경하여 다른 결과를 반환하는 경우. <br>
예시:  <br>
상품조회 및 결제를 진행하는 동안 다른 사용자가 그 상품을 결제를 하여 상품 결제이후 상품 조회 수량이 엉뚱한 값을 불러옴 <br>
 쿠폰 발급이후 동일 쿠폰 수량을 조회했을 때 엉뚱한 값을 불러옴<br>

해결법:  <br>
트랜잭션 격리 수준 설정: Repeatable Read 이상으로 설정. <br>

•	Phantom Read: 한 트랜잭션이 동일한 조건으로 여러 번 데이터를 조회할 때, 중간에 다른 트랜잭션이 데이터를 삽입하거나 삭제하여 결과가 달라지는 경우. <br>
예시:  <br>
상품 결제 중 관리자가 새로운 상품을 추가하여 조회 결과가 달라지는 상황.<br>
쿠폰 발급 중 관리자가 새로운 쿠폰을 추가하여 조회 결과가 달라지는 상황<br>

해결법:  <br>
트랜잭션 격리 수준 설정: Serializable로 설정하여 팬텀 리드를 방지. <br><br>



Day 2: DB의 동시성 문제와 제어 방법 <br>
•	DB Transaction Isolation Levels: 트랜잭션 간 간섭을 제어하는 단계.<br>
-READ UNCOMMITTED: commit이나 rollback에 상관없이 트랜잭션의 데이터 변경 내용을 다른 트랜잭션이 읽는 것을 허용하는 트랜잭션 격리 수준<br>
-READ COMMITTED:	트랜잭션이 commit, rollback 으로 완료되면 다른 트랜잭션에서 조회가 가능한 트랜잭션 격리 수준입니다.<br>
-REPEATABLE READ: 트랜잭션 범위 내에서 조회한 내용이 항상 동일함을 보장하는 트랜잭션 격리 수준입니다. 또한, MySQL의 InnoDB에서 기본으로 사용하는 트랜잭션 격리 수준<br>
-SERIALIZABLE: 모든 작업을 하나의 트랜잭션에서 처리하는 것과 같이 동작하는 가장 높은 트랜잭션 격리 수준입니다.<br>
한 트랜잭션에서 읽고 쓰는 레코드를 다른 트랜잭션에서는 절대 접근할 수 없습니다. <br>

레벨 |	Dirty Read	| Non-Repeatable Read	| Phantom Read |
|-----------|----------------|----------------|---------------|
Read Uncommitted| 가능	        | 가능	| 가능
Read Committed	| 불가능	| 가능	| 가능
Repeatable Read	| 불가능	| 불가능| 가능
Serializable	| 불가능	| 불가능| 불가능



•	S-lock: 공유 잠금한 트랜잭션이 데이터 항목에 대하여 읽기(Read) 만 가능<br>
•	다른 트랜잭션도 읽기(Read) 만을 실행 할 수 있는 형태<br>
•	X-lock: 전용 잠금한 트랜잭션은 데이터 항목에 대하여 읽기(Read) 와 기록(Write) 모두 가능 다른 트랜잭션은 읽기(Read) 와 기록(Write) 모두 할 수 없음<br>
•	Optimistic Lock: 충돌 감지 기반, 충돌 가능성이 낮은 환경에 적합.<br>
•	Pessimistic Lock: 충돌 방지 기반, 충돌 가능성이 높은 환경에 적합.<br>




각 제어 방식의 장단점

|구분       |	S-lock / X-lock           | Optimistic Lock                   | Pessimistic Lock                |
|-----------|---------------------------|-----------------------------------|---------------------------------|
충돌 방지   | 명시적 잠금으로 충돌 방지|	충돌 발생 후 검증 및 재시도   | 충돌 발생 자체를 원천 차단
성능        | 잠금으로 성능 저하           | 충돌 빈도가 낮을 경우 성능 우수| 잠금으로 인한 성능 저하
구현 복잡도 |	데이터베이스 지원으로 간단 | 중간 (버전 번호 관리 필요)     | 복잡 (잠금 관리 및 해제 필요)
동시성 처리 |	동시성 낮음                |	동시성 높음                  |	동시성 낮음
적합한 환경 |일반적인 트랜잭션 환경       |충돌 가능성이 낮은 고동시성 환경 | 충돌 가능성이 높은 환경


포인트 충전/ 조회: 낙관적 락 - 포인트 충전시에 충돌 가능성이 낮고 동시성이 높은 환경에 적합<br>
상품 재고 및 차감: 비관적 락, 분산 락 - 상품 조회시 충돌 가능성이 높고 데이터 변경이 잦은 경우 적합.<br>
주문/결제: 바관적 락 주문/결제 시 충돌 가능성이 높고 데이터 변경이 잦은 경우 적합.<br><br>


Day 3: DB Lock 활용한 동시성 제어<br>
•	DB Lock: 데이터베이스에서 여러 트랜잭션이 동시에 데이터를 액세스하거나 수정하는 경우, 데이터의 일관성과 무결성을 보장하기 위해 사용되는 메커니즘입니다.<br>
•	S-lock (Shared Lock): 공유 락은 트랜잭션이 데이터를 읽기(Read) 할 때 설정됩니다.<br>
•	X-lock (Exclusive Lock): 배타 락은 트랜잭션이 데이터를 **수정(Write)**할 때 설정됩니다.<br>
•	Transaction Management: 트랜잭션 관리란 데이터베이스에서 트랜잭션이 ACID 속성(원자성, 일관성, 고립성, 지속성)을 충족하도록 처리하는 프로세스를 말합니다.<br>
